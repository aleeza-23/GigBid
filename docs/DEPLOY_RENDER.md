# Deploying on Render

Three web services and a Postgres database, from the blueprint in
[`render.yaml`](../render.yaml). About 25 minutes, most of it waiting for builds.

```
reviewer's browser
      |
      v
gigbid-web  (Next.js)  --/api/*-->  gigbid-api  (FastAPI)  ---->  gigbid-gigsim
                        server-side proxy            |            (marketplace)
                                                     v
                                               gigbid-db (Postgres)
```

The browser only ever talks to the web service. `apps/web/src/app/api/[...path]/route.ts`
proxies to the API server-side, which keeps the session cookie first-party and means the
API needs no CORS for the browser.

## Before you start

| | |
|---|---|
| The repo pushed to GitHub | Render deploys from a branch, not from your laptop |
| A Groq API key | Free. Set as `OPENAI_API_KEY`; the variable is named for the OpenAI-compatible shape, not the vendor |
| A Together AI key | Free credits. Used for embeddings only, because Groq serves no embeddings endpoint |
| A Render account | The free plan is enough, with the caveats below |

If you would rather not create a Together account, see
[Embeddings without a second provider](#embeddings-without-a-second-provider).

## 1. Deploy the blueprint

In Render: **New > Blueprint**, pick the repository, let it read `render.yaml`, apply.

It creates `gigbid-gigsim`, `gigbid-api`, `gigbid-web` and the `gigbid-db` database. All
three services will build. The API and the web app will not work yet, because three of
their variables are URLs that do not exist until the services do.

## 2. Set the secrets

Generate a token for the simulator and use the same value in both places:

```bash
python -c "import secrets; print(secrets.token_urlsafe(24))"
```

**gigbid-gigsim > Environment**

| Variable | Value |
|---|---|
| `GIGSIM_API_TOKEN` | the token you just generated |

**gigbid-api > Environment**

| Variable | Value |
|---|---|
| `GIGSIM_API_TOKEN` | the same token |
| `OPENAI_API_KEY` | your Groq key |
| `TOGETHER_API_KEY` | your Together key |
| `REVIEWER_PASSWORD` | a password you will send in the private submission comment |

`APP_SECRET_KEY` is generated by Render. Leave it alone: changing it signs everyone out.

## 3. Wire the services to each other

Each service has a URL now, of the form `https://gigbid-api.onrender.com`. Take them from
the dashboard, do not guess them, because Render appends a suffix when a name is taken.

| Service | Variable | Value |
|---|---|---|
| gigbid-api | `GIGSIM_BASE_URL` | the gigsim URL |
| gigbid-api | `CORS_ORIGINS` | the web URL |
| gigbid-web | `API_BASE_URL` | the api URL |

No trailing slashes. Then **Manual Deploy > Deploy latest commit** on the API and the web
service so they pick the values up.

## 4. Check it

```bash
curl -s https://gigbid-api.onrender.com/health | python -m json.tool
```

Four things in that output decide whether a reviewer will see a working app:

- `marketplace.status` is `"ok"`. If it is `unavailable`, `GIGSIM_BASE_URL` is wrong or the
  two `GIGSIM_API_TOKEN` values differ.
- `persistence.checkpointer` is `"postgres"` and `survives_restart` is `true`. Anything
  else means pending approvals die when the instance sleeps, which on a free plan is
  several times a day.
- `models.offline` is `false`. If it is `true`, `OPENAI_API_KEY` did not arrive and every
  draft will be a placeholder.
- `degraded` is empty, or lists only things you meant to leave degraded.

Then open the web URL, sign in as `reviewer` with the password you set, and analyse a job
from the inbox. The first request wakes the API and encodes the corpus, so give it a
minute; after that it is quick.

## What the free plan actually gives you

Worth knowing before a grader clicks the link, and worth saying in your submission note.

**Services sleep after 15 minutes of inactivity.** The next request takes 30 to 60 seconds
while the instance starts. The link stays live; it is just slow on the first click. If that
matters, the $7 Starter plan keeps one service awake, and the one to pay for is the web
service, since it is what gets clicked.

**512MB of RAM.** That is why `render.yaml` sets `EMBED_BACKEND=api`:
sentence-transformers pulls torch, a 2.5GB install needing roughly 2GB of RAM to serve, and
the instance would be killed while loading the model. The `api` backend calls an
OpenAI-compatible endpoint serving `BAAI/bge-base-en-v1.5`, so the model is still
open-weight and the service stays small. It is a *different* embedder from the
`BAAI/bge-small-en-v1.5` that produced `evals/results/`, which is why those numbers were
measured locally and the deployed app is the demo rather than the measurement.

**Free Postgres is deleted 30 days after creation.** Check the expiry date in the dashboard
against when your grades are released. Two ways out: upgrade the database, or point
`DATABASE_URL` at a free database that does not expire, such as Neon or Supabase. Both give
a `postgresql://` connection string that drops straight into `DATABASE_URL`;
`agent/checkpointer.py` already strips a SQLAlchemy `+psycopg` suffix if yours has one.

**No free background workers.** The scheduled worker is not in the blueprint. Nothing in
the reviewer's path needs it: "Analyse this job" in the UI runs the same graph the worker
would. To add it anyway, create a Background Worker service (paid) with
`startCommand: python -m worker.scheduler` and the same environment as the API, or run
`make worker` on your own machine against the deployed GigSim.

**Build minutes are limited.** The web build is the slow one. Avoid redeploying it just to
change an environment variable on a different service.

## Embeddings without a second provider

If you would rather not sign up for Together, set these on the API service instead:

| Variable | Value | Consequence |
|---|---|---|
| `EMBED_BACKEND` | `lsa` | No second provider, no torch. TF-IDF plus SVD fitted on the corpus itself, which is **not** an open-weight pretrained model, so it does not satisfy B2 and every results file it touches records `is_pretrained: false`. Fine for a UI demo, not for a reported number. |

Or use OpenRouter in place of Together: set `EMBED_BASE_URL` to
`https://openrouter.ai/api/v1` and `OPENROUTER_API_KEY` to your key. `rag/embeddings.py`
reads `TOGETHER_API_KEY`, `OPENROUTER_API_KEY` or `EMBED_API_KEY`, in that order.

To run the real `local` backend on Render, put the API on the 2GB Standard plan and change
its build command to `pip install -e ".[persistence,rag]"` and `EMBED_BACKEND=local`. The
first request then loads a 130MB model, so expect a slow cold start on top of the sleep.

## When something is wrong

| What you see | What it usually is |
|---|---|
| Web app returns 503 with "API unreachable at ..." | `API_BASE_URL` is unset, misspelled, or has a trailing slash. The message names the URL it tried. |
| Sign-in fails with "Internal Server Error" | The API is asleep or crashed, and the proxy could not reach it. Check the API's logs, not the web app's. |
| Sign-in fails with "incorrect username or password" | `REVIEWER_PASSWORD` differs from what you typed. It is read at request time, so no redeploy is needed after changing it. |
| "Marketplace unavailable" on the inbox | `GIGSIM_BASE_URL` wrong, tokens mismatched, or GigSim asleep. The banner has a retry button and the trace id. |
| Every draft is a placeholder | `models.offline` is true in `/health`: no provider key reached the API. |
| Approvals vanish after a while | `persistence.checkpointer` is not `postgres`. The free instance sleeps and in-memory state goes with it. |
| API build fails on `psycopg` | The `persistence` extra needs `psycopg[binary]`; make sure the build command is `pip install -e ".[persistence]"` and `PYTHON_VERSION` is 3.11. |

Logs are per service in the dashboard. Every API response carries an `X-Trace-Id` header,
and `data/audit/traces/` inside the instance holds the spans for a run, though that is
ephemeral storage and goes when the instance restarts.

## What to put in the submission

- The **web** URL, not the API one.
- `reviewer` and the `REVIEWER_PASSWORD` you set, in the private comment.
- A note that the first click may take a minute while the free instance wakes, and that
  the deployed app uses the API embedding backend rather than the local one the committed
  results were measured with.
